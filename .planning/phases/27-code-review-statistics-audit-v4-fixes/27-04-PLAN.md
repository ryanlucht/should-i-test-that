<objective>
Fix infeasible-prior state propagation (SA-3), reporting consistency between raw and effective prior (SA-4), dollar-threshold tie detection (SA-5), and the plain-English explanation using wrong prior mean (CR-4).

These fixes depend on Plan 01 (correct effective-prior metrics) because the reporting/display layer needs to consume correct metrics.

**Design invariant (resolves Codex contradiction concern):**
The engine layer (evsi.ts, net-value.ts) continues to use `defaultDecision: 'dont-ship'` as a type-safe sentinel for infeasible priors. This is NOT a fabricated decision -- it is the correct conservative default when no feasible prior mass exists. The `isInfeasiblePrior` flag lives on `EVSICalculationResults` (hook level, NOT `EVSIResults` engine level) because the hook is where the effective-prior metrics are computed and cached. The UI reads `isInfeasiblePrior` from the hook result and suppresses interpretive cards that would be misleading.

This is one consistent invariant: **infeasible priors produce zero-dollar engine results with a warning, and the UI gates all interpretive copy on the `isInfeasiblePrior` flag.** No `defaultDecision: null` needed (would require changing a union type across the entire codebase for a rare edge case).

SA-3: Propagate `isInfeasiblePrior: true` on hook results. UI suppresses waterfall, supporting cards, export when infeasible.

SA-4: Waterfall and export use effective feasible prior mean. Show both raw input and effective prior when they differ materially.

SA-5: `computeIsTie()` compares in lift units using `threshold_L` from the engine. No more comparing percentage-point prior mean against dollar threshold values.

CR-4: Fix plain-English explanation to use effective prior when truncation is material.

Purpose: Ensure UI/export accurately reflects the engine's actual decision-making when truncation or infeasibility matters.
Output: Consistent reporting between engine and display layer with targeted tests.
</objective>

    **SA-5 fix: Fix computeIsTie in AdvancedResultsSection.tsx:**

    The current `computeIsTie` compares `priorMean` (percentage points) against `thresholdValue` (which can be dollars). Fix by comparing in lift-unit space using the engine's `threshold_L`:

    Replace the entire function:
    ```typescript
    /**
     * Determine whether the effective prior mean is at the shipping threshold.
     * All comparisons in lift-unit space (decimal) for unit consistency (SA-5).
     *
     * Uses threshold_L from the engine (already normalized to decimal lift units
     * regardless of whether user entered dollars or percentage), so dollar
     * thresholds are handled correctly.
     *
     * @param effectivePriorMeanDecimal - Effective prior mean in decimal lift units
     * @param threshold_L - Threshold in decimal lift units (from engine)
     */
    function computeIsTie(
      effectivePriorMeanDecimal: number,
      threshold_L: number,
    ): boolean {
      const TIE_EPSILON = 0.0001; // 0.01 percentage points in decimal lift
      return Math.abs(effectivePriorMeanDecimal - threshold_L) < TIE_EPSILON;
    }
    ```

    const isTie = computeIsTie(

    );
