<objective>
Fix the HIGH severity stale-values bug (CR-1): after completing all wizard sections, editing an input field without re-submitting the section leaves results, share links, and PNG exports reflecting the old store values.

**Root cause analysis (addresses Codex review concern):**
Forms use React Hook Form (RHF) local state. Zustand `setInput()` is only called on successful form submit (via `handleSubmit(onSubmit)`), NOT during editing. This means:
1. User completes all sections (store has valid values, all sections marked complete)
2. User scrolls back and edits a field in section 0
3. RHF updates its local state, but Zustand store still has the OLD values
4. Results section reads from Zustand store -- shows stale results
5. Share/export serialize from Zustand store -- produce stale URLs/PNGs

**Solution architecture:**
The fix operates at TWO levels:
1. **Store level:** Add `invalidateSection(n)` action that removes section n and all downstream from `completedSections`
2. **Form level:** Each form watches for RHF dirty state changes. When a completed section's form becomes dirty (user edits any field), the form fires an `onSectionDirty` callback provided by CalculatorPage, which calls `invalidateSection`. This prevents Results access until the user re-submits.

**Why NOT write-through on every keystroke:** Writing every RHF field to Zustand on onChange would bypass Zod validation (storing invalid intermediate values like empty strings, partial numbers). The forms intentionally batch-validate and only flush to Zustand on valid submit. The invalidation approach preserves this architecture.

**visitorUnitLabel exception (Codex review):** `visitorUnitLabel` is presentational only -- it does not affect EVSI calculations. However, it is simpler and safer to invalidate uniformly on any field edit (including visitorUnitLabel) because: (a) the user must click Continue to re-complete anyway, (b) special-casing one field adds complexity for no user benefit, and (c) the label IS included in share URLs and exports, so it technically can produce stale output.

Purpose: Prevent incorrect results from being displayed, shared, or exported when inputs have been changed.
Output: Store with invalidation logic, form-level dirty detection, CalculatorPage wiring, and tests.
</objective>

    // CR-1: Detect when a completed section becomes dirty during editing.
    // RHF tracks dirty state internally via formState.isDirty.
    // When this form belongs to a completed section and the user edits any field,
    // we fire onSectionDirty so CalculatorPage can invalidate downstream sections.
    // This fires on the FIRST edit only (isDirty transitions from false to true).
    const { formState: { isDirty } } = methods;  // or destructure from existing formState usage

    useEffect(() => {

    IMPORTANT: RHF's `isDirty` compares current values to `defaultValues`. After a successful submit that resets defaultValues (which our forms do NOT do -- they use `handleSubmit` without `reset`), `isDirty` stays false until the user actually changes something. This is exactly what we want: it fires when the user first touches a field after the section was completed.

    IMPORTANT: After the section is re-submitted (user clicks Continue), the form's `defaultValues` are still the original mount values, so `isDirty` will remain true. But this is fine because `invalidateSection` is idempotent -- calling it when the section is already invalid is a no-op. And when `markSectionComplete` is called on successful re-submit, the section is re-added to `completedSections`.
