## Summary

This review covers the stats engine v3 audit fix files: calculation modules (EVSI, net-value, feasibility, sample-size), UI components (forms, results, export), state management, URL codec, and associated tests. The codebase is well-documented with thorough mathematical comments for audit, good input validation guards, and defensive NaN handling throughout.

## Critical Issues

### CR-01: Unit mismatch in truncation comparison (AdvancedResultsSection)

**File:** `src/components/results/AdvancedResultsSection.tsx:128-137`
**Issue:** `rawPriorMean` is computed from `priorLow` and `priorHigh` which are in **percentage form** (e.g., 5.0 for 5%). `effectivePriorMean` from the calculation engine is in **decimal lift form** (e.g., 0.05 for 5%). The comparison `Math.abs(effectivePriorMean - rawPriorMean) > TRUNCATION_DISPLAY_THRESHOLD` compares values in incompatible units. For any asymmetric prior interval (e.g., [-5, 15]), `rawPriorMean` = 5.0 while `effectivePriorMean` ~= 0.05, making `truncationMaterial` always true regardless of actual truncation.

The ExportCard correctly handles this at lines 147-152 by dividing `rawPriorMean` by 100 before comparing. AdvancedResultsSection skips this conversion.

This bug is masked in tests because the test fixtures use a symmetric interval (mean = 0) where percentage and decimal representations are identical.

**Fix:**
```typescript
// Line 128: Convert rawPriorMean to decimal lift units for comparison
const rawPriorMean = (priorLow + priorHigh) / 2;
const rawPriorMeanDecimal = rawPriorMean / 100;

// Line 137: Compare in consistent units (both decimal lift)
const truncationMaterial = Math.abs(effectivePriorMean - rawPriorMeanDecimal) > TRUNCATION_DISPLAY_THRESHOLD;
```

Also update line 197 and line 203 where `effectivePriorMean` is displayed -- it is already in decimal, so `(effectivePriorMean * 100).toFixed(1)` at line 203 is correct, but verify that `priorMean` (the alias for `rawPriorMean`) used at line 197 for display is also consistent (it uses percentage form which is correct for display).

Add a test with an asymmetric interval (e.g., priorIntervalLow=-2, priorIntervalHigh=10, priorMean=4%) to verify the truncation annotation does NOT appear when truncation is not actually material.

## Warnings

### WR-01: Missing `mode` discriminant prop on ExportButton

**File:** `src/components/results/AdvancedResultsSection.tsx:314-321`
**Issue:** `ExportButton` is called without the required `mode` prop. The component's type is a discriminated union `BasicModeProps | AdvancedModeProps` where both variants require `mode` explicitly. At runtime, `props.mode` is `undefined`, which means:
- Line 124 (`if (mode === 'advanced')`) in ExportButton is false
- Line 154 (`mode === 'basic'`) is also false
- The component falls through to "basic" code paths in ternary expressions (e.g., line 178 uses `props.evpiResults` which doesn't exist)

TypeScript appears to not catch this, possibly due to the structural overlap of the union variants. At runtime this may cause crashes or incorrect behavior when accessing `props.evpiResults` on what is actually an advanced-mode call.

**Fix:**
```tsx
<ExportButton
  mode="advanced"
  evsiResults={results}
  sharedInputs={inputs}
  prior={prior}
  testDurationDays={inputs.testDurationDays ?? undefined}
  analysisName={analysisName}
  effectivePriorMean={results?.effectivePriorMean}
/>
```

### WR-02: Stale worker reference captured in cleanup closure

**File:** `src/hooks/useEVSICalculations.ts:356-363`
**Issue:** The cleanup function captures `workerRef.current` at line 356 *before* the async `runWorker()` completes. The `runWorker` function creates the Worker and assigns it to `workerRef.current` (line 303) asynchronously. If the effect cleanup runs before the Worker is created, `currentWorker` is null, and the actual Worker is never terminated. If cleanup runs after, it works correctly. This is a race condition where rapid input changes can leak Worker instances.

The comment at line 355 acknowledges the pattern but the captured ref is from before the async operation starts.

**Fix:**
Move the cleanup to also check `workerRef.current` directly, since the ref itself is stable across renders:
```typescript
return () => {
  requestIdRef.current++;
  // Terminate any worker that may have been created by the async operation
  if (workerRef.current) {
    workerRef.current.terminate();
    workerRef.current = null;
  }
};
```
Note: This is safe because the ref object identity is stable across renders. The `finally` block in `runWorker` also terminates, providing defense-in-depth.

### WR-03: Redundant `computeEffectivePriorMetrics` call in `finalResults` memo

**File:** `src/hooks/useEVSICalculations.ts:380-385`
**Issue:** `computeEffectivePriorMetrics` is called a second time inside the `useMemo` for `finalResults` (line 381), even though the same computation was already performed in the `useEffect` at line 256. While the comment acknowledges this is "deterministic" and "idempotent," it adds unnecessary computation on every result change. If `computeEffectivePriorMetrics` were ever changed to be non-deterministic (unlikely but possible), this could introduce inconsistency.

**Fix:** Store the `effectiveMetrics` result from the useEffect in a ref or state variable and read it in the useMemo, rather than recomputing. This also makes the data flow more explicit.

### WR-04: Missing keyboard event handling on expandable timing costs row

**File:** `src/components/results/ValueBreakdownCard.tsx:66-79`
**Issue:** The timing costs row uses `role="button"` and `tabIndex={0}` with both `onClick` and `onKeyDown` handlers, which is good. However, the `onKeyDown` handler only handles Enter and Space keys. While this covers the standard keyboard interaction for buttons, the `div` element with `role="button"` should ideally use a `<button>` element instead to get native keyboard and screen reader support for free, including focus styling.

**Fix:** Replace the `div[role="button"]` with a `<button>` element styled as a flex row:
```tsx
<button
  type="button"
  className={cn(
    'w-full flex justify-between items-baseline cursor-pointer rounded px-1 -mx-1 transition-colors',
    'hover:bg-muted/50'
  )}
  onClick={() => setIsExpanded(!isExpanded)}
  aria-expanded={isExpanded}
>
```

### IN-01: `console.error` calls in production code paths

**File:** `src/hooks/useEVSICalculations.ts:328,337` and `src/components/export/ExportButton.tsx:210`
**Issue:** `console.error` calls remain in production code. While these are reasonable for error diagnostics in catch blocks, they could be replaced with a structured error reporting mechanism in production builds.
**Fix:** Consider adding error boundary or error tracking service integration. Low priority for v1.

### IN-02: Large useMemo dependency on `props` object in ExportButton

**File:** `src/components/export/ExportButton.tsx:150`
**Issue:** The `chartPrior` useMemo includes `props` in its dependency array (line 150). Since `props` is a new object reference on every render, this memo will recompute on every render, defeating its purpose. The relevant individual props (`mode`, `props.prior` for advanced mode) should be listed instead.
**Fix:**
```typescript
// Extract the specific dependency before the useMemo
const advancedPrior = mode === 'advanced' ? props.prior : undefined;

const chartPrior: PriorDistribution = useMemo(() => {
  if (mode === 'advanced' && advancedPrior) {
    return advancedPrior;
  }
  // ... basic mode logic
}, [mode, sharedInputs.priorIntervalLow, sharedInputs.priorIntervalHigh, advancedPrior]);
```

### IN-03: eslint-disable comment for exhaustive-deps in UncertaintyPriorForm

**File:** `src/components/forms/UncertaintyPriorForm.tsx:326-327`
**Issue:** The `setValue` function from react-hook-form is excluded from the dependency array with an eslint-disable comment explaining it's not memoized. While the comment is thorough, this is a known react-hook-form limitation. The approach is correct but the pattern should be noted for future maintainers upgrading react-hook-form (which may stabilize `setValue` in future versions).
**Fix:** No code change needed. The comment is adequate. This is informational only.
